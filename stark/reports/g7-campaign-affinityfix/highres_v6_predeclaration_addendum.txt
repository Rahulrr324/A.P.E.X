1. WHY A NEW RUN IS NEEDED (v5 outcome, evidence already on disk)
   v5 verified API-level separation (worker readback=0x1, collector
   readback=0x2, observed CPUs [0] vs [1]) yet still failed coverage:
   5/8 collector-active (B) compute-bound execs recorded 0-1 samples in
   [t0,t1], and the 3 B execs that did sample show ~1.9-2.2x iteration-time
   inflation vs their A partners (e.g. B9 pair1: 26893 us span vs ~7500-8400 us
   A; B7: median 4796/4810 us vs 2937/2408 us A).

   ROOT CAUSE (verified 2026-10-07 via GetLogicalProcessorInformationEx,
   RelationProcessorCore, before this addendum was written):
     physical core 0 = logical processors {0,1}  (SMT pair)
     physical core 1 = {2,3}   core 2 = {4,5}   core 3 = {6,7}
     E-cores (no SMT): {8}, {9}, {10}, {11}
     union of all LPs = 0xFFF = machine system mask (self-validating)
     => CPU1 IS the SMT sibling of CPU0.
   A worker that saturates P-core0 starves its sibling (explains 0 samples in
   ~7 ms compute windows), and a collector that actually runs on CPU1 steals
   execution resources from the worker (explains the ~2x slowdown). Measuring
   on CPU1 therefore CANNOT satisfy the goal: "measurement must not compete
   with the benchmark thread." The requirement to verify the machine's real
   mask before choosing CPU1 is exactly what triggers this deviation.

2. v6 CHANGE (single variable: collector target CPU selection rule)
   Predeclared selection rule, computed in-process at startup from
   GetLogicalProcessorInformationEx(RelationProcessorCore):
     collector_cpu = the lowest-numbered logical CPU that
       (a) is present in the system mask,
       (b) is not CPU0 (the worker), and
       (c) does NOT share a physical core with CPU0
           (its core's LP set does not contain 0).
   On this machine the rule evaluates to CPU2 (physical core 1).
   If no such CPU exists, the diagnostic aborts with exit 3 (no run).
   "preferably CPU 1" is intentionally NOT followed; CPU1 fails (c), and
   section 1 documents why CPU1 cannot provide a non-perturbing measurement
   on this hardware. This is a deviation from the preference, NOT from the
   requirements: pinning must be to a different logical CPU, effective
   affinity of BOTH threads must be verified, and separation must be proven
   per-thread (never assumed from the process mask).

   Process mask will be set to {CPU0, collector_cpu} (readback-verified) only
   so both per-thread pins are realizable; separation is still proven by
   per-thread SetThreadAffinityMask readback + per-sample observed CPU.
