SECTION 1 — EXACT FORMULAS (from source)

Location: stark/src/phase1/diagnostics/bm_b7_diagnostic.cpp, function
calibrate(), lines ~733–807. Formulas:

  POPULATION FOR PAIRING
    minimal[i].total_samples_sec  (size = measurement_count per valid replicate)
    instrumented[i].total_samples_sec
    Pairing key: SAME index i (replicate index) AND SAME index j (iteration index).
    Pre-condition enforced: minimal.size() >= required_replicates AND
    instrumented.size() >= required_replicates AND every replicate in BOTH
    conditions valid (otherwise INCONCLUSIVE). Then:
      a = minimal[i].total_samples_sec[j]
      b = instrumented[i].total_samples_sec[j]
      sizes must be equal per i (otherwise INCONCLUSIVE).
      a must be > 0 and finite, and b must be finite (otherwise INCONCLUSIVE).

  PAIRED OVERHEAD (per observation)
    pct_ij = 100.0 * (b - a) / a
    Sign convention: POSITIVE = instrumented slower than minimal partner;
    NEGATIVE = instrumented faster than minimal partner.
    Denominator: the MINIMAL partner timing a (never the instrumented value,
    never the mean, never the max). Zero/near-zero a is rejected outright
    (inconclusive) — there is no special near-zero handling; a <= 0 -> INCONCLUSIVE.
    No clamping: pct_ij is used as observed.

  WORST-CASE OVERHEAD (reported statistic)
    worst = maximum SIGNED pct_ij over ALL valid pairs (all i, all j).
    Initialized worst = 0.0; updated only when pct > worst (so if all pairs are
    negative, worst remains negative — but that cannot happen here because
    have_pair forces worst to the first pct, then max). Final:
      c.worst_case_overhead_pct = worst
    Threshold: <= 10.0 % (kCalibWorstOverheadThresholdPct), signed maximum,
    not absolute. Note: a single extreme positive pair can dominate.

  MEAN OVERHEAD (reported statistic)
    mean_min  = (sum over all a) / n_total
    mean_instr= (sum over all b) / n_total
    c.mean_overhead_pct = 100.0 * (mean_instr - mean_min) / mean_min
    Absolute value compared to 2.0 % threshold.
    This is a POOLED mean, NOT the mean of the per-pair pct_ij values.

  MEDIAN-DEVIATION (reported statistic)
    Pooled medians (via summarize(), which uses production compute_statistics
    for mean/median/p95/stdev/min/max and linear interpolation for p25/p75):
      s_min  = summarize(pooled_min).median_us
      s_instr= summarize(pooled_instr).median_us
    c.median_deviation_pct = 100.0 * |s_instr - s_min| / s_min
    Threshold: <= 2.0 %.

  STATUS LOGIC
    PASS  iff computable AND mean_ok AND worst_ok AND median_ok
    FAIL   iff computable AND NOT (mean_ok AND worst_ok AND median_ok)
    INCONCLUSIVE otherwise (insufficient/invalid data, non-positive/non-finite
    denominators, paired sample-count mismatch, etc.)
    Thresholds:
      kCalibMeanOverheadThresholdPct       = 2.0
      kCalibWorstOverheadThresholdPct      = 10.0
      kCalibMedianDeviationThresholdPct    = 2.0

IMPORTANT DISTINCTION (often confused): the reported worst_case_overhead_pct is
an extreme SIGNED paired value (single observation), while mean_overhead_pct and
median_deviation_pct are pooled/summary quantities. This is why the reported
worst-case can be huge even when means/medians are near zero.

SECTION 4 — IS THE WORST-CASE DRIVEN BY A HANDFUL OF OBSERVATIONS?

Answer: UNVERIFIED — hypothesis only, not established by existing evidence.

What is known:
  - The reported worst-case is the MAXIMUM SIGNED paired value across 300 pairs.
  - In all three corrected runs, the worst-case is an order of magnitude above the
    10% threshold while the pooled mean is near zero and pooled medians differ by
    <= 3.6%. That pattern is CONSISTENT WITH a worst-case driven by a small number
    of extreme positive pairs, but it is ALSO consistent with a broad but sparse
    distribution of moderately positive pairs plus noise.
  - The diagnostic's stdout does not expose the distribution, so concentration is
    not determinable from preserved evidence.

Conclusion: the report statement "driven by a handful of observations" is a
plausible hypothesis, not a confirmed finding. The one thing that IS confirmable
from the source is that the reported worst-case statistic is structurally
vulnerable to a single extreme pair: it is the signed maximum, not a trimmed or
robust statistic.

  FAIL condition: computable AND NOT(pass).

  run2: mean -0.4367 -> OK

  run3: mean 1.4555 -> OK

        median-deviation 0.7181 -> OK

The reported FAIL notes match the source formatting exactly (the note lists the
failing checks). So the three FAIL results are internally consistent with the
implementation and thresholds. No discrepancy found.

One nuance worth stating explicitly: worst-case threshold is a SIGNED <= 10%
test. That means an extreme NEGATIVE worst-case (instrumented faster than minimal
in its worst signed pair) would trivially pass the 10% test. The failures here
are because the worst signed pair is a large POSITIVE number, i.e. a single
(i, j) where the instrumented iteration was much slower than its minimal partner.
That is exactly the outlier scenario the report is asking about — but which
specific pair(s) it is cannot be identified from preserved evidence.
